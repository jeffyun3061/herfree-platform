# Isolated staging database helper (review only)

`infra/scripts/staging-isolated-db.sh` prepares a new disposable database on the existing staging-only MySQL host without changing the existing staging database. A newly created per-run account receives grants only on the disposable schema; it does not reuse the existing staging application account. The account and schema are removed only after the original service is restored and verified. An uncertain account creation requires manual reconciliation. This is still a draft: it is not wired into a workflow, is not a promotion gate, and must not be used as production-release evidence on its own.

The caller must ensure the staging EC2 host is the intended isolated host, the external staging test route is protected, the candidate is pinned, and the last known staging image is recoverable. The script restricts container selection to the staging compose project and checks that the running API is healthy and matches the recorded current image, private MySQL networking, one active isolation at a time, a successful staging predeployment backup, and a newly absent `hfqa<8 hex>` database before changing anything. It journals the original environment and image in a permission-restricted directory. Passwords are not printed.

Three explicit phases are needed:

1. `prepare <run>` creates the isolated DB and schema-scoped grant and switches the staging configuration to it. Only the staging configuration is changed, with the admin IP gate restricted to loopback. `pin <run> <immutable ECR digest>` records the sole allowed QA image. After that image is deployed, `verify <run>` checks the running staging container, exact image, isolated datasource and health before tests may proceed. None of these commands by itself authorizes promotion.
2. `restore-config <run>` restores the original staging configuration. It refuses to overwrite a configuration that no longer matches either the saved original or this run's generated test configuration. The caller must then restore the recorded original image using the normal rollback script and verify it is healthy.
3. `finalize <run>` checks the saved configuration, recorded and running image, running datasource, and health before revoking the test schema grant and dropping only the database owned by that run. The state record is removed only after successful cleanup.

Each command takes the existing staging release lock while it executes, but the lock is not held between commands. An orchestrator must serialize the whole multi-step run and keep a durable record outside its runner. It must not promote an image while cleanup or state is uncertain. If a command is interrupted between recording creation intent and confirming creation, the helper refuses automatic deletion and requires manual reconciliation. A runner cancellation, a lost connection, missing state, an unexpected configuration edit, or an unhealthy restored service must not be reported as a clean run.

The review-only `orchestrate-isolated-staging.sh` provides host-side `start`, `verify` and `cleanup` phases. Before any action it checks the exact AWS account, region and staging instance through IMDSv2 and requires the staging deployment guard. It serializes coordinator invocations, pins the candidate digest before deployment, and verifies the live datasource afterward. Cleanup restores the recorded original configuration and image before the helper checks health and removes its isolated database. Interrupted or failed actions retain the state for reconciliation. This host coordinator is not yet wired to a GitHub workflow, frontend build, browser tests, or production promotion.

The draft deployment guard uses the same release lock and refuses unrelated staging deployments while an isolation record exists. An orchestrated deploy or rollback must pass `HERFREE_ISOLATED_QA_RUN` matching the record and the recorded QA or restored configuration; incomplete or conflicting records block it. While the QA configuration is active it accepts only the pinned QA digest; once the original configuration is restored, it accepts only a rollback to the recorded original image. Reconciliation remains available to quarantine interrupted deployments. This guard is a second protection, not a substitute for end-to-end serialization or independent instance verification.

This helper alone does not resolve the different `main`/`develop` frontend trees, create a protected QA branch, change IAM policy, attach the tested rollback image to production deployment, or verify production backup recovery. Those remain separate work and no staging or production resources should be changed until the complete workflow is reviewed and verified.

## Read-only frontend preflight

`infra/scripts/verify-isolated-frontend.py` checks a separately created, Basic-protected QA branch against the exact local and remote `main` commit, its successful Amplify build, and the staging health endpoints. For pre-merge review, `--candidate-pr <number>` instead requires the remote PR head and QA branch to match the exact checked-out commit. PR mode is pre-merge evidence only and never authorizes promotion; the final merged commit must be verified separately. It pins the expected AWS account, app, region and staging API before sending QA credentials. Supply those credentials only through `ISOLATED_QA_BASIC_USERNAME` and `ISOLATED_QA_BASIC_PASSWORD`; do not pass them on the command line or reuse production credentials. Its IAM caller needs read access to that specific QA branch. No IAM permissions are granted by the script.

This is a preflight only: it does not validate the staging instance identity or database isolation, execute browser tests, verify cleanup, or authorize promotion. Its output explicitly records those gates as incomplete. Never treat its success as a production deployment approval.

`infra/scripts/run-isolated-staging-smoke.sh` runs the existing read-only browser smoke suite only after this preflight passes. Set the QA branch, exact commit, matching `PLAYWRIGHT_BASE_URL` and QA-only Basic credentials in the environment; set `ISOLATED_QA_PR` to the PR number for pre-merge testing. It refuses mutation tests and never promotes an image. It is not wired into the release workflow; mutation tests and their database-isolation proof require separate orchestration.

## Protected branch creation helper

`infra/scripts/create-isolated-frontend.py` prepares an exact PR-head QA branch with Basic authentication enabled in the creation request and automatic builds disabled. It checks the account, pinned application, remote PR and QA branch refs before making a request and verifies the resulting branch settings afterward. Provide QA-only credentials in `ISOLATED_QA_BASIC_USERNAME` and `ISOLATED_QA_BASIC_PASSWORD`; they are sent to AWS via a temporary mode-0600 request file and are never placed in command arguments or printed. A failed or interrupted request may have created a branch and requires manual inspection before any retry. This helper does not run automatically, start a build, perform browser tests, or authorize production deployment. IAM permission must be separately reviewed and approved; IAM branch scoping alone does not enforce the helper's Basic-auth settings.

The manually dispatched `prepare-isolated-qa-frontend.yml` is pinned to PR #195 and its exact candidate and QA refs. It uses the existing staging-only test credentials, serializes against staging releases, and is restricted to `main` and the named repository. It cannot run until this workflow exists on `main` and the separately reviewed, branch-scoped creation and read permissions are granted. A successful run only creates the protected branch with builds disabled; it is not staging test evidence.

`verify_staging_route.py` is a read-only, fail-closed routing check. It verifies the AWS account, the fixed staging EC2 instance, running and SSM-online status, and DNS records, then connects to the instance's checked IPv4 address while validating TLS for the staging hostname. It rejects redirected or oversized health responses. This is only a point-in-time routing check; it does not verify the isolated database or authorize promotion, and deployments behind an intermediary or IPv6 must be assessed separately.

`verify-isolated-staging.py --run <8 hex> --image <immutable ECR digest>` adds a point-in-time check after isolation has already been established. It checks the staging route, compares the installed staging tools with the local reviewed files, and asks the fixed staging instance to verify its matching run, image and isolated datasource; it then checks the route again. It submits an SSM command but creates no database and changes no deployment. It is a draft building block, not a lock, continuous guarantee, browser test, cleanup proof or promotion gate. The caller must establish serialization and independently verify frontend provenance and cleanup.

`run-isolated-share-qa.sh` is a draft runner for the pinned PR #195 candidate and its protected QA branch. It checks both the isolated backend and the exact frontend before and after sequential desktop Chromium, mobile Chromium and iPhone WebKit browser tests. Tests create disposable accounts and posts, so the caller must serialize all staging changes and establish the isolated database before invoking it; it does not start isolation, retain a lock, clean up the host, or authorize promotion. Test-only QA Basic credentials are passed in the environment. The test disables retained browser traces and screenshots. A failure or interruption requires staging reconciliation, even if the browser checks had passed earlier.

`staging-qa-tools.py` is a draft host-side installer and reconciler for the five reviewed QA scripts. It checks the fixed staging instance via IMDSv2, validates the caller-provided source hashes, snapshots original files and modes in a protected record, and holds the staging release lock during installation and restoration. Restore refuses active isolation, pending deployments and unexpected file edits. It does not authenticate the supplied hashes, hold a lock between operations, start or test the application, restore the database, stop the server or authorize promotion. The enclosing workflow must pin trusted source hashes, serialize the entire session and verify actual cleanup; an interrupted or inconsistent record requires reconciliation.

`package-staging-qa-tools.py` produces a deterministic, size-limited archive of only those tools and their installer from a specified local commit. It verifies the repository identity and that the PR #196 head matches both before and after packaging, rejects symlinks and unexpected file modes, and includes a per-tool SHA-256 manifest. It creates a new local file only; it neither uploads nor installs it. The caller must independently review the exact commit, verify the bundle digest at the destination and avoid placing secrets in SSM commands. [AWS warns that Run Command parameters can be logged in plaintext.](https://docs.aws.amazon.com/systems-manager/latest/userguide/running-commands.html)

`build-isolated-frontend.py` starts or inspects a build only for the pinned candidate QA branch after checking the AWS account, Basic authentication, disabled automatic builds, API origin and remote refs. It refuses to start while a job is active, does not retry ambiguous start responses, and requires the exact commit in a successful job before calling that build verified. AWS documents that a `RELEASE` job starts from the latest branch revision, so an unchanged ref and an exact result must be verified rather than assumed. See the [AWS StartJob API](https://docs.aws.amazon.com/amplify/latest/APIReference/API_StartJob.html). The separately reviewable `infra/aws/isolated-qa-build-policy.proposed.json` is not applied: `GetBranch` can reveal Basic credentials, and `StartJob` incurs build usage. The job ARN scope follows the [AWS Amplify service authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_amplify.html). This build check does not run staging tests or authorize production promotion.

The QA Git branch must remain fixed during the build and test; checking its ref before and after cannot exclude a change-and-revert race. `infra/aws/isolated-qa-git-protection.proposed.json` documents a proposed read-only branch lock with administrator enforcement and no force pushes or deletion. It applies only to `qa-4160aee7de7a-4160aee7`, not `main` or `develop`. The protection is not applied; a change to GitHub branch protection requires separate approval. The lock should be removed or changed only after QA and cleanup are complete.
