# 개발자 결정 체크리스트

이 문서는 Herfree를 개발하면서 “AI가 대신 구현해도 되지만, 백엔드 개발자인 내가 이해하고 결정해야 하는 부분”을 정리한 것이다.
작업 속도를 늦추지 않기 위해 모든 항목을 한 번에 완벽히 끝내지 않는다.
대신 배포 전, 운영 전, 면접 준비 전에 반복해서 확인한다.

## 사용 방법

- `결정 필요` 항목은 내가 직접 선택한다.
- `AI 도움 가능` 항목은 구현, 초안 작성, 테스트 추가를 맡길 수 있다.
- `면접 설명` 항목은 왜 그렇게 했는지 내 말로 설명할 수 있어야 한다.
- 아직 모르면 `보류`로 두고, 배포 차단인지 후속 개선인지 구분한다.

## 빠른 분류

| 구분 | 내가 직접 결정 | AI 도움 가능 |
| --- | --- | --- |
| DB | migration 적용 시점, 백업/복구 정책 | migration 파일 작성, 테스트 추가 |
| 보안 | 토큰/세션 정책, 관리자 권한 범위 | 취약점 점검, 방어 코드 구현 |
| 운영 | 로그 보관 기간, 장애 알림 방식 | 운영 문서 초안, 체크리스트 정리 |
| 배포 | 배포 순서, 롤백 기준 | 빌드 검증, runbook 정리 |
| 제품 | 운영자가 실제로 써야 할 관리자 기능 | 관리자 UI/API 구현 |

## 1. DB와 마이그레이션

### 결정 필요

- [ ] 운영 DB 변경은 Flyway로만 적용한다.
- [ ] 배포 전 RDS snapshot 또는 백업을 만든다.
- [ ] migration 실패 시 배포를 중단할지, 이전 버전으로 되돌릴지 정한다.
- [ ] 데이터 삭제는 hard delete, soft delete, 익명화 중 어떤 정책을 쓸지 정한다.

### 내가 이해해야 할 것

- `ddl-auto=update`는 운영에서 위험하다.
- migration은 DB 구조 변경 이력을 코드처럼 남기는 장치다.
- 이미 적용된 migration 파일은 원칙적으로 수정하지 않고 새 migration을 추가한다.
- 컬럼 삭제나 타입 변경은 데이터 손실 가능성이 있어 백업과 롤백 계획이 필요하다.

### 면접 설명

> 운영 DB는 JPA 자동 변경에 의존하지 않고 Flyway migration으로 스키마 변경 이력을 관리했습니다. 배포 전 백업을 만들고, migration 실패 시 앱 배포를 중단하는 흐름으로 운영 위험을 줄였습니다.

## 2. 인증과 세션

### 결정 필요

- [ ] access token 만료 시간을 정한다.
- [ ] refresh token을 도입할지, 도입한다면 HttpOnly cookie와 회전 정책을 쓸지 정한다.
- [ ] 관리자 계정에 MFA를 언제 도입할지 정한다.
- [ ] 계정 정지, 탈퇴, 비밀번호 재설정 정책을 운영자에게 어떻게 노출할지 정한다.

### 내가 이해해야 할 것

- access token은 짧게, refresh token은 더 엄격하게 관리한다.
- 브라우저 저장소에 남는 토큰은 XSS 위험에 노출될 수 있다.
- 로그인 실패 응답은 계정 존재 여부를 알려주면 안 된다.
- 비밀번호 재설정 token과 URL은 로그에 남기면 안 된다.

### 면접 설명

> 로그인 실패 응답과 처리 시간을 맞춰 계정 열거 가능성을 줄였고, 비밀번호 재설정 URL이나 token이 로그에 남지 않도록 했습니다.

## 3. 권한과 개인정보

### 결정 필요

- [ ] 비공개 게시글, 문의, 개인 기록의 조회 권한 기준을 정한다.
- [ ] 운영자가 볼 수 있는 개인정보 범위를 최소화한다.
- [ ] 회원 탈퇴 후 게시글, 상담, 문의 데이터를 어떻게 처리할지 정한다.
- [ ] 개인정보 보관 기간과 삭제 요청 처리 절차를 정한다.

### 내가 이해해야 할 것

- 화면에서 숨기는 것만으로는 보안이 아니다. API와 query에서 막아야 한다.
- 관리자 권한도 최소 권한 원칙을 적용해야 한다.
- 개인정보 삭제는 서비스 정책, 법적 요구, 장애 대응 가능성을 함께 봐야 한다.

### 면접 설명

> 비공개 데이터는 프론트에서 숨기는 것에 그치지 않고, 서비스와 repository query 단계에서 소유자 또는 운영자만 조회 가능하도록 제한했습니다.

## 4. 로그와 모니터링

### 결정 필요

- [ ] 운영 로그를 어디에 저장할지 정한다. 예: CloudWatch
- [ ] 로그 보관 기간을 정한다.
- [ ] 장애 알림을 받을 채널을 정한다. 예: 이메일, Slack, 문자
- [ ] 개인정보, token, reset URL이 로그에 남지 않는지 점검한다.

### 내가 이해해야 할 것

- 로그는 장애 추적을 위한 것이지 개인정보 보관소가 아니다.
- 운영 실패를 로그만 남기고 성공 처리하면 사용자는 문제를 모른다.
- 인증/인가 로그는 너무 자세하면 보안 위험, 너무 적으면 장애 추적이 어렵다.

### 면접 설명

> 운영 로그에서 비밀번호, 토큰, reset URL 같은 민감 정보는 제외하고, 장애 추적에 필요한 요청 흐름과 실패 원인만 남기는 기준을 정했습니다.

## 5. 파일 업로드와 S3

### 결정 필요

- [ ] 허용할 파일 확장자와 content type을 정한다.
- [ ] 최대 업로드 크기를 정한다.
- [ ] 이미지 원본을 직접 공개할지, API proxy를 통해 제공할지 정한다.
- [ ] S3 bucket public access 차단 여부를 확인한다.

### 내가 이해해야 할 것

- 사용자가 보낸 content type만 믿으면 안 된다.
- 큰 파일을 한 번에 메모리로 읽으면 서버가 죽을 수 있다.
- presigned URL은 편하지만 만료 시간과 권한 범위를 조심해야 한다.

### 면접 설명

> S3 객체를 조회할 때 먼저 metadata를 확인하고, 허용된 content type과 크기만 제한된 방식으로 읽도록 해서 메모리 위험을 줄였습니다.

## 6. 배포와 롤백

### 결정 필요

- [ ] 배포 순서를 정한다. 예: 백업 -> 빌드 -> migration -> 앱 배포 -> smoke test
- [ ] 배포 실패 시 롤백 기준을 정한다.
- [ ] 배포 후 반드시 확인할 기능을 정한다.
- [ ] 운영 중인 서비스에 영향이 적은 시간대를 정한다.

### 내가 이해해야 할 것

- 코드는 되돌릴 수 있어도 DB migration은 쉽게 되돌리기 어렵다.
- 배포 후에는 로그인, 회원가입, 게시글, 이미지, 메일 같은 핵심 흐름을 확인해야 한다.
- 롤백은 “이전 커밋으로 돌아가기”만이 아니라 DB와 환경변수 상태까지 포함한다.

### 면접 설명

> 배포 전 build/test를 통과시키고, DB 백업과 migration 적용 여부를 확인한 뒤 smoke test로 핵심 사용자 흐름을 검증하는 절차를 문서화했습니다.

## 7. 관리자 운영

### 결정 필요

- [ ] 운영자 계정을 개인별로 발급할지 정한다.
- [ ] SUPER_ADMIN 권한을 몇 명에게 줄지 정한다.
- [ ] 신고 처리, 게시글 숨김, 회원 정지 사유를 기록할지 정한다.
- [ ] 운영자가 직접 처리하면 안 되는 작업을 정한다.

### 내가 이해해야 할 것

- 공유 관리자 계정은 추적이 어렵다.
- 관리자 기능은 편의보다 오남용 방지가 중요하다.
- 개인정보 삭제, DB 수정, 권한 부여는 운영 절차가 필요하다.

### 면접 설명

> 관리자 기능은 신고 처리와 콘텐츠 관리 중심으로 두고, 권한 부여와 개인정보 처리는 최소 권한과 감사 가능성을 기준으로 분리했습니다.

## AI에게 맡겨도 되는 일

- 반복적인 테스트 코드 추가
- 문서 초안 작성
- API 명세와 DTO 동기화 확인
- 보안 취약 가능성 grep/checklist 점검
- 빌드 실패 원인 추적
- 작은 리팩터링

## 내가 직접 확인해야 하는 일

- 운영 secret 값 입력
- AWS 콘솔에서 RDS, S3, SMTP, 도메인 설정
- 관리자 계정 발급
- DB 백업/복구 가능 여부 확인
- 배포 버튼을 누르는 최종 판단
- 개인정보/보관/삭제 정책 결정

## 작업 속도를 늦추지 않는 원칙

1. 막히는 개념은 20분만 학습하고, 결정이 필요하면 문서에 보류로 남긴다.
2. 배포 차단 항목과 후속 개선 항목을 분리한다.
3. AI에게 구현을 맡겨도, 운영 위험이 있는 선택은 내가 고른다.
4. 커밋 메시지와 문서에 “왜”를 남긴다.
5. 면접 준비는 코드 설명보다 의사결정 설명을 먼저 연습한다.
