# Herfree 배포/롤백 런북

> 운영 환경은 Amplify 프론트엔드와 EC2의 API·로컬 MySQL이다. 아래 명령은
> 개발 담당자를 위한 절차이며, 로그나 이슈에 비밀번호·인증코드·건강정보를 기록하지 않는다.

## 현재 AWS 배포 절차

1. 변경 PR에서 CI와 보안 검사를 통과시키고, 배포할 커밋과 이전 정상 이미지 digest를 기록한다.
2. 운영 DB 백업 상태와 복구 절차를 확인한다. 스테이징은 기존 인스턴스를 테스트할 때만 사용하고 종료 후 중지 상태를 확인한다.
3. 운영과 격리된 스테이징에서 같은 커밋의 프론트와 백엔드를 검증한다. 게시글 권한, 로그인, 댓글, 일지와 변경 기능을 확인한다. 실제 사용자 데이터는 테스트에 사용하지 않는다.
4. `.github/workflows/release-backend.yml`의 `staging` 실행이 성공하면 해당 커밋의 검증된 이미지가 표시된다. 스테이징의 develop 프론트가 동일한 릴리스가 아니면 이 작업은 중단되므로, 실패 이유를 확인하고 프론트 배포를 맞춘 뒤 다시 실행한다.
5. DB 변경의 호환성과 백업을 확인한 뒤 같은 워크플로의 `production`을 현재 `main`에서 실행한다. 프로덕션 환경 승인과 취약점 검사, 배포 전 백업 및 상태 확인이 필요하다. 스테이징에서 통과한 **동일 이미지 digest**가 없으면 진행하지 않는다.
6. API가 정상인 것을 확인한 뒤 `.github/workflows/deploy-production-frontend.yml`을 현재 `main`에서 실행한다. 운영 프론트 자동 빌드가 켜져 있으면 `main` 병합 시 먼저 배포될 수 있으므로, 호환성이 필요한 변경의 배포 순서를 사전에 관리한다. 자동 빌드를 일시 중지했다면 완료 후 원래 설정을 복구한다.
7. 운영 배포 결과, 배포 버전, 테스트와 스테이징 중지 여부를 기록한다. 로그인·게시글·댓글·일지와 관리자 기능은 권한별로 확인한다. 실사용자 글이나 개인일지를 수정해 테스트하지 않는다.

`promote-tested-pr206.yml`은 PR 206의 특정 테스트 결과만 검증하는 예외용 작업이다. 다른 릴리스의 검증 근거로 재사용하지 않는다. 일반 배포의 환경·권한이 준비되지 않았거나 스테이징 검증이 실패하면 보안 게이트를 건너뛰지 말고 원인을 해결한다.

**실패 대응:** 스테이징 실행 실패나 중단 시에도 인스턴스 중지 여부를 별도로 확인한다. 운영 배포의 자동 복구가 실패했거나 DB 마이그레이션이 포함됐다면 현재 버전과 백업을 확인하고 개발 담당자가 복구 범위를 판단한다. 이미지 롤백만으로 DB 변경이 되돌아간다고 가정하지 않는다.

## 브랜치와 커밋

- `main`: 운영 배포 기준
- 작업 브랜치: 기능/보안 수정
- 운영 배포 전에는 백엔드 build와 프론트 lint/build가 모두 통과해야 한다.

## 배포 전 체크

```bash
cd backend
./gradlew build

cd ../frontend
npm run lint
npm run build
```

확인 항목:

- `.env.prod`가 git에 포함되지 않았는지
- `JWT_SECRET`, DB 비밀번호, SMTP 비밀번호, S3 키가 git에 없는지
- `APP_MAIL_MODE=smtp`
- `TRUSTED_PROXY_CIDRS`가 실제 프록시 CIDR만 가리키는지
- `CORS_ALLOWED_ORIGINS`가 실제 프론트 도메인인지

## 배포 후 smoke test

| 순서 | 테스트 | 기대 결과 |
|------|--------|-----------|
| 1 | `/actuator/health` | 200 |
| 2 | 로그인 | 테스트 계정으로 로그인하고 인증 쿠키가 정상 동작 |
| 3 | 비밀번호 재설정 | 실제 메일 수신 |
| 4 | 게시글 작성/수정/삭제 | 정상 처리 |
| 5 | 이미지 업로드/조회 | S3 저장 및 API 프록시 조회 |
| 6 | 문의/상담 게시판 | 본인 또는 운영자만 조회 |
| 7 | 관리자 신고 처리 | 숨김/복구 정상 |

쓰기·삭제·메일 수신 검사는 격리된 스테이징 테스트 계정과 데이터로 수행한다.
운영에서는 실제 사용자 데이터에 영향을 주지 않는 범위만 확인한다.

## 롤백

1. 현재 장애 증상을 기록한다.
2. 직전 정상 배포 커밋을 확인한다.
3. 서버에서 직전 이미지/커밋으로 재배포한다.
4. DB migration이 포함된 배포라면 롤백 전 개발자가 migration 영향을 확인한다.
5. smoke test를 다시 수행한다.

## 장애 시 우선순위

1. 인증/로그인 장애
2. DB 연결 장애
3. 비밀번호 재설정 메일 장애
4. 이미지 업로드/조회 장애
5. 관리자 기능 장애

사용자 개인정보나 토큰이 로그에 노출된 정황이 있으면 즉시 배포를 중단하고 로그 접근 범위를 제한한다.
