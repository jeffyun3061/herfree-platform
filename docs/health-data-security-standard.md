# Herfree 건강정보 보안·개인정보 관리 기준

문서 버전: 1.0  
기준일: 2026-07-16  
적용 범위: Herfree의 설계, 개발, 테스트, 배포, 운영, 장애 대응, 외주 인수인계

이 문서는 Herfree에서 가장 우선하는 보안·개인정보 기준이다. 다른 문서와 충돌하면 더 엄격한 기준을 적용하고, 충돌 사실과 최종 결정을 `docs/decision-log.md`에 남긴다.

> 이 기준은 법률 자문이나 공인 인증을 대신하지 않는다. "최고 등급", "완전한 보안", "법적 문제 없음"을 주장하기 위한 문서가 아니라, 건강정보 서비스에 필요한 통제를 빠뜨리지 않고 증거로 남기기 위한 내부 기준이다.

## 1. 기준과 판정 방법

Herfree는 건강·질병, 증상, 투약, 수면, 스트레스, 상담 내용을 다룰 수 있으므로 일반 커뮤니티보다 높은 수준으로 관리한다.

- 법적 기준: 개인정보 보호법상 건강정보를 민감정보로 취급한다.
- 개발 기준: OWASP ASVS 5.0 Level 2를 기본 목표로 하고, 인증·접근통제·암호화·관리자 기능·건강정보에는 Level 3 취지의 추가 통제를 적용한다.
- API 기준: OWASP API Security Top 10의 객체·기능 권한, 자원 제한, 설정 오류, 외부 API 신뢰 문제를 변경마다 확인한다.
- 사고 대응: NIST SP 800-61 Rev. 3의 준비, 탐지, 대응, 복구, 사후 개선 흐름을 따른다.
- 인프라 기준: AWS Well-Architected의 최소 권한, 암호화, 분리, 복구 검증 원칙을 적용한다.

### 판정 기호

| 표시 | 의미 | 공개 배포 |
| --- | --- | --- |
| `PASS` | 코드, 설정, 테스트, 운영 증거까지 확인 | 가능 |
| `CODE` | 코드만 구현됨. 실제 AWS·외부 연동 증거 필요 | 조건부 |
| `DECISION` | 운영자 또는 개인정보 책임자의 정책 결정 필요 | 불가 |
| `BLOCK` | 민감정보 노출·복구 실패로 이어질 수 있는 미완료 | 불가 |
| `ROADMAP` | 현재 규모에서는 보완 통제로 운영 가능하나 확장 전 필요 | 조건부 |

체크박스를 채웠다는 사실만으로 `PASS`가 되지 않는다. 명령 출력, 스크린샷, AWS 설정 내보내기, 테스트 리포트, 승인자와 승인 시각 중 하나 이상의 증거가 있어야 한다.

## 2. 책임과 승인

| 역할 | 책임 | 금지 |
| --- | --- | --- |
| 서비스 운영 책임자 | 처리 목적, 보유기간, 이용약관, 민감정보 동의, 공지와 신고 최종 승인 | 개발자에게 법적 결정을 전부 위임 |
| 개인정보 보호책임자 또는 담당자 | 처리방침, 요청 처리, 유출 판단, 위탁사 관리 | 연락처 없는 형식적 지정 |
| 개발 책임자 | 권한, 암호화, migration, 로그, 복구, 테스트 증거 | 운영 DB 즉석 수정 |
| 배포 승인자 | staging 결과와 production 변경 범위 확인 | 본인이 만든 변경을 증거 없이 단독 승인 |
| 운영자 | 신고·문의·콘텐츠·회원 제재 | DB·환경변수·AWS root 직접 조작 |
| 외부 유지보수자 | 계약 범위의 최소 권한 작업 | 운영 데이터 로컬 반출 |

최소 2인 승인이 불가능한 초기 운영에서는 production 배포 전에 다음 두 기록을 분리한다.

1. 개발자가 `docs/templates/release-security-review.md`를 작성한다.
2. 서비스 운영 책임자가 개인정보·운영 항목을 확인하고 승인 시각을 남긴다.

## 3. 데이터 분류

| 등급 | 예시 | 기본 처리 |
| --- | --- | --- |
| `D0 공개` | 공지, 공개 칼럼, 공개 영상 정보 | 무결성·운영 권한 보호 |
| `D1 계정` | 이메일, 닉네임, 가입일, 계정 상태 | 최소 조회, 로그 원문 금지 |
| `D2 커뮤니티` | 게시글, 댓글, 신고, 문의 | 공개 범위와 작성자 권한 분리 |
| `D3 민감 건강정보` | 증상, 투약, 수면, 스트레스, 일지 메모, 비공개 상담 | 별도 동의, 강한 접근통제, 암호화, 최소 집계 |
| `D4 인증 비밀` | 비밀번호, JWT, reset token, OAuth secret, DB·SMTP secret | 평문 저장·로그·채팅·Git 금지 |

### D3 필수 규칙

- 목적이 확정되지 않은 필드는 수집하지 않는다.
- 개인별 원문은 본인 기능 외에 재사용하지 않는다.
- 운영자 화면은 원문 대신 집계 또는 처리에 필요한 최소 정보만 제공한다.
- 통계는 서로 다른 사용자 수 기준의 최소 표본을 적용한다. 동일 사용자의 반복 기록으로 공개 조건을 충족시키지 않는다.
- 표본이 작거나 특정 사용자를 추정할 수 있으면 결과를 숨긴다.
- production 데이터를 개발·QA·면접 시연에 복사하지 않는다.
- 백업, 로그, 검색 인덱스, 캐시까지 동일한 삭제·접근 기준을 적용한다.

## 4. 현재 프로젝트 엄격 판정

이 표는 2026-07-16 코드 확인 기준이다. AWS와 외부 콘솔을 실제 확인하지 않은 항목은 `PASS`로 표시하지 않는다.

| 영역 | 현재 상태 | 근거 또는 남은 일 |
| --- | --- | --- |
| 로그인 계정 열거 방어 | `CODE` | 외부 오류 통일과 비밀번호 해시 유사 비용 테스트 존재 |
| 이메일 중복·정규화 | `CODE` | 정규화, DB unique, 동시 중복 예외 처리 존재 |
| 비밀번호 재설정 | `CODE` | token hash, 만료, 1회 사용, 민감 로그 방지 테스트 존재 |
| 비공개 게시판 | `CODE` | 소유자·운영자 query 범위와 테스트 존재 |
| 개인일지 객체 권한 | `CODE` | record 조회·삭제 시 소유자 불일치에 404 처리 |
| 파일 업로드·조회 제한 | `CODE` | 타입·크기·S3 prefix·제한 읽기 검증 존재 |
| 민감정보 별도 동의 | `CODE` | 가입 요청과 `V32`에 별도 동의 기록 존재 |
| 관리자 감사 | `CODE` | `admin_audit_logs`, 역할 감사, request ID 존재 |
| 운영 profile·secret 차단 | `CODE` | profile guard, secret scan, release env 검사 존재 |
| N+1 회귀 방지 | `CODE` | 목록 query count 통합 테스트 존재 |
| 운영 RDS·S3·CloudWatch | `BLOCK` | 실제 private RDS, KMS, 알람, IAM, 복원 증거 필요 |
| OAuth secret 교체 | `BLOCK` | 대화·화면에 노출된 기존 secret 전부 폐기·재발급 필요 |
| 관리자 강한 인증 | `BLOCK` | MFA 또는 관리 API 접근 게이트가 실제 적용됐다는 증거 필요 |
| 탈퇴·재가입·보존 정책 | `DECISION` | 이메일·비밀번호·OAuth·reset token·닉네임 원문은 제거한다. 동의·감사·게시물 보존기간과 재가입 정책 승인 필요 |
| 개인정보 처리방침 | `DECISION` | 실제 운영 주체, 주소, 책임자, 위탁사, 국외 이전, 보유기간 확정 필요 |
| 공개 건강 통계 | `CODE` | 서로 다른 사용자 20명 이상, 항목별 5명 이상일 때만 공개하도록 구현·테스트 |
| DB 전송 암호화 | `BLOCK` | RDS CA 검증을 포함한 TLS JDBC 연결과 RDS TLS 강제 필요 |
| 건강정보 DB 보호 | `DECISION` | RDS 저장 암호화는 필수. 일지 memo 등 필드 단위 KMS envelope 암호화 도입 범위 결정 필요 |
| 자동 보존·파기 | `CODE` | 이벤트·reset token·감사 로그 파기 job과 탈퇴 즉시 비식별화 구현. 운영 보존기간 승인·실행 증거 필요 |
| 사고 대응 체계 | `BLOCK` | 연락망, 권한, 72시간 타이머, 공지 초안, 모의훈련 기록 필요 |
| refresh token 회전 | `ROADMAP` | 현재 access token을 sessionStorage에 저장. XSS 영향 축소를 위해 HttpOnly cookie 기반 회전 구조 검토 |
| 분산 rate limit | `ROADMAP` | 현재 메모리 기반이면 다중 인스턴스 전환 전 Redis 등 중앙 저장소 필요 |
| 독립 보안 검증 | `BLOCK` | 공개 전 OWASP ZAP 또는 동등 DAST와 수동 권한 테스트, 가능하면 외부 점검 필요 |

### 현재 공개 배포 판정

`BLOCK`과 `DECISION` 항목이 남아 있으므로 이 문서 기준 production 공개는 `NO-GO`다. staging에서 기능 검증은 가능하다.

## 5. DB·마이그레이션 엄격 체크리스트

### 설계

- [ ] D3 컬럼과 해당 목적, 접근 주체, 보유기간을 데이터 사전에 기록했다.
- [ ] 이메일, OAuth 식별자, 건강 기록, 게시글 작성자 ID의 결합 가능성을 검토했다.
- [ ] 관리자 조회 DTO에 불필요한 이메일·원문·건강정보가 포함되지 않는다.
- [ ] 모든 사용자 소유 데이터 query에 `user_id` 또는 명시적 운영 권한 조건이 있다.
- [ ] 공개 집계는 `COUNT(DISTINCT user_id)` 최소 표본과 소수 셀 억제를 사용한다.
- [ ] 개인정보 삭제가 원본 DB, 검색 인덱스, 캐시, S3, 분석 로그에 미치는 영향을 정의했다.

### migration

- [ ] 운영 schema 변경은 Flyway 새 버전 파일로만 추가한다.
- [ ] 이미 적용된 migration은 수정·삭제하지 않는다.
- [ ] migration에 `DROP`, 컬럼 타입 축소, `NOT NULL`, 대량 `UPDATE`, index 재구성이 있으면 별도 검토서를 작성했다.
- [ ] expand → backfill → application switch → contract 순서로 무중단 변경을 설계했다.
- [ ] 운영과 같은 MySQL major/minor에서 migration dry run을 완료했다.
- [ ] 운영 데이터량을 가정한 실행 시간과 lock 범위를 측정했다.
- [ ] 실패 시 앱 rollback만으로 충분한지, DB restore가 필요한지 적었다.
- [ ] 배포 직전 snapshot 또는 PITR 시점을 만들고 식별자를 기록했다.

### 운영 DB

- [ ] production RDS는 public access가 꺼져 있다.
- [ ] 3306은 API 보안 그룹에서만 접근 가능하다.
- [ ] DB 애플리케이션 계정에는 DDL·GRANT·FILE 권한이 없다.
- [ ] migration 계정과 애플리케이션 계정을 분리했다.
- [ ] 저장 암호화와 자동 백업, 삭제 보호, PITR을 켰다.
- [ ] JDBC는 RDS CA를 검증하는 TLS 연결을 사용한다.
- [ ] DB parameter에서 TLS가 아닌 연결을 거부한다.
- [ ] slow query log와 Performance Insights를 켜되 SQL parameter 원문 노출 범위를 확인했다.
- [ ] 월 1회 별도 staging DB로 복원하고 RTO·RPO를 기록한다.
- [ ] 백업 삭제 권한은 운영 DB 수정 권한과 분리한다.

### 성능·확장

- [ ] 목록 API는 기본 20, 최대 50 등 상한이 있다.
- [ ] 대량 export는 일반 목록 API와 분리하고 권한·감사·시간 제한을 둔다.
- [ ] 목록 query count 회귀 테스트가 데이터 건수에 비례해 증가하지 않는다.
- [ ] 새 검색·정렬 조건에는 `EXPLAIN` 결과와 index 근거가 있다.
- [ ] P95 DB query 시간, connection 사용률, lock wait 알람 기준을 정했다.
- [ ] 캐시에 D3 원문을 저장하지 않거나, 저장 시 암호화·짧은 TTL·삭제 연동을 적용했다.

## 6. 애플리케이션 보안 체크리스트

### 인증·세션

- [ ] 로그인 실패 응답이 계정 존재·정지 여부를 비밀번호 검증 전에 드러내지 않는다.
- [ ] 로그인, 회원가입, reset, OAuth callback에 사용자와 IP 기반 rate limit이 있다.
- [ ] 비밀번호 정책은 길이, 유출 비밀번호 차단, 재사용 방지를 검토했다.
- [ ] access token 만료와 권한 변경 반영 지연을 문서화했다.
- [ ] 관리자 세션은 일반 사용자보다 짧고 MFA를 요구한다.
- [ ] 로그아웃·탈퇴·정지·비밀번호 변경 시 기존 세션을 무효화한다.
- [ ] OAuth state, redirect URI, client secret, provider 응답 검증 테스트가 있다.

### 권한

- [ ] 모든 `/{id}` API에 다른 사용자 ID를 넣는 BOLA/IDOR 테스트가 있다.
- [ ] 프론트에서 숨기는 것과 별개로 Controller·Service·Repository에서 권한을 제한한다.
- [ ] 비공개 검색·정렬·개수·에러 차이로 존재를 추론할 수 없다.
- [ ] 관리자 권한 부여·회수·정지·닉네임 초기화가 감사 로그에 남는다.
- [ ] 관리자 목록에서 이메일은 기본 마스킹하고, 원문 열람은 별도 사유와 감사 기록을 요구한다.
- [ ] SUPER_ADMIN은 최소 인원이며 공용 계정이 없다.

### 입력·출력·파일

- [ ] DTO validation과 DB 길이 제한이 일치한다.
- [ ] HTML/Markdown 렌더링 시 XSS 방어와 CSP를 검증한다.
- [ ] 목록과 검색의 page size, keyword 길이, 정렬 필드를 허용 목록으로 제한한다.
- [ ] 업로드는 확장자뿐 아니라 실제 파일 시그니처, content type, 크기를 검사한다.
- [ ] S3 key는 사용자 prefix와 랜덤 ID를 사용하고 임의 URL을 신뢰하지 않는다.
- [ ] 이미지 처리 라이브러리와 외부 OAuth/SMTP 응답에 timeout·크기 제한이 있다.
- [ ] SSRF가 가능한 URL 입력은 허용 도메인과 protocol을 제한한다.

### 의존성과 공급망

- [ ] lockfile을 커밋하고 CI에서 고정 설치한다.
- [ ] Dependabot, CodeQL, secret scan 결과를 주간 검토한다.
- [ ] critical/high 취약점은 예외 사유와 만료일 없이 방치하지 않는다.
- [ ] 배포 이미지는 commit SHA로 식별하고 staging과 production이 동일 digest를 사용한다.
- [ ] GitHub Actions는 최소 권한과 OIDC를 사용하고 장기 AWS key를 저장하지 않는다.
- [ ] SBOM 생성과 release artifact 보관을 확장 전 도입한다.

## 8. 로그·감사·탐지 체크리스트

로그는 증거이면서 새로운 개인정보 저장소가 될 수 있다. 원문보다 식별자와 흐름을 남긴다.

절대 로그 금지:

- 비밀번호, JWT, reset token·URL, OAuth code·token, client secret
- 이메일 원문, 건강 메모, 상담·문의·게시글·댓글 원문
- request/response body 전체, presigned URL, DB·SMTP·AWS secret

필수 로그:

- UTC 시각, 환경, 서비스 버전, request ID, 내부 사용자 ID 또는 비가역 식별자
- endpoint template, HTTP method/status, 오류 분류, 처리 시간
- 관리자 actor ID, 대상 종류·ID, 행위, 결과, 사유 코드
- 배포 SHA, migration 버전, 설정 버전

운영 통제:

- [ ] CloudWatch 로그 그룹은 staging과 production을 분리한다.
- [ ] 로그 저장 암호화와 최소 권한을 적용한다.
- [ ] 애플리케이션 로그는 기본 30일 후 자동 파기한다.
- [ ] 관리자·권한 감사 로그 보유기간은 법률·운영 검토 후 별도로 정한다.
- [ ] 접근 로그 조회 자체를 감사한다.
- [ ] 401/403/429/5xx, 관리자 변경, 비공개 접근 거부 급증 알람이 있다.
- [ ] 로그 표본의 개인정보 원문 포함 여부를 월 1회 검사하고 기록한다.
- [ ] incident 시 로그 보존 연장은 승인된 사건 범위에만 적용한다.

## 9. 인프라·복구 체크리스트

- [ ] AWS root 계정 MFA와 사용 금지 정책이 있다.
- [ ] 사람 계정, EC2 role, GitHub deploy role을 분리한다.
- [ ] production과 staging의 VPC, DB, S3, secret, 로그를 분리한다.
- [ ] API, RDS, S3, 백업은 저장·전송 중 암호화한다.
- [ ] 외부 공개는 443만 허용하고 API·DB 관리 포트를 닫는다.
- [ ] WAF 또는 동등 통제로 rate limit, 악성 요청, bot 급증을 완화한다.
- [ ] EC2/ECR/OS/JDK/DB의 보안 업데이트 책임과 기한을 정한다.
- [ ] RDS snapshot, PITR, S3 versioning, 필요 시 Object Lock을 검토한다.
- [ ] 백업은 production 삭제 권한과 분리하고 암호화한다.
- [ ] 월 1회 복원, 분기 1회 전체 장애 훈련을 한다.
- [ ] RPO와 RTO를 운영자가 승인했다.

## 10. 사고 대응

### 등급

| 등급 | 예시 | 초기 대응 |
| --- | --- | --- |
| `SEV-1` | 타인 건강정보 노출, 관리자 탈취, DB·백업 유출, secret 공개 | 15분 내 배포·접근 중지, 책임자 호출 |
| `SEV-2` | 인증 전체 장애, 대량 5xx, 데이터 쓰기 오류, 복구 불확실 | 30분 내 rollback 또는 기능 차단 |
| `SEV-3` | 일부 외부 연동 장애, 성능 저하, UI 오류 | 영향 제한 후 정상 절차 수정 |

### 공통 순서

1. 사람과 데이터 보호를 우선하고 신규 배포·관리자 변경을 중지한다.
2. request ID, 시각, 계정 ID, 배포 SHA, 영향 endpoint를 기록한다.
3. 노출된 secret 폐기, 계정 잠금, 경로 차단 등 확산을 막는다.
4. 로그와 snapshot을 보존하되 민감 원문을 새 장소로 복사하지 않는다.
5. 영향 데이터 종류, 사용자 수, 최초·최종 시각, 공격·오류 경로를 산정한다.
6. 건강정보 유출 가능성이 있으면 법정 통지·신고 시한을 즉시 확인한다.
7. 직전 정상 이미지 rollback 또는 검증된 백업 복원을 수행한다.
8. 사용자 공지는 확인된 사실, 영향, 조치, 사용자가 할 일을 구분해 작성한다.
9. 복구 후 5영업일 내 원인, 탐지 실패, 재발 방지, 담당자와 기한을 기록한다.

개인정보보호위원회 안내상 민감정보 유출, 외부 불법 접근, 1천 명 이상 유출 등은 72시간 이내 신고 대상이 될 수 있다. 유출 인지 시 법률 담당자와 KISA 118에 즉시 확인한다.

3. 누가 어떤 화면·API로 볼 수 있는가.

5. 유출 시 어떤 피해가 가능한가.
6. 공개·관리자 통계에서 재식별을 어떻게 막는가.
7. 동의서·처리방침 변경이 필요한가.

## 13. 증거 중심 관리

다른 개발자, 외주 의뢰인, 면접관에게는 "보안을 신경 썼다"가 아니라 다음 증거로 설명한다.

- ADR: 선택한 구조와 거부한 대안
- Flyway: 스키마 변경 이력
- 권한 테스트: 타인 ID, 역할, 비공개 검색 차단
- query count 테스트: N+1 회귀 방지
- release review: 배포 SHA, migration, smoke, rollback 기준
- incident drill: RTO·RPO와 발견된 개선점
- 감사 로그: 관리자 변경 추적
- 데이터 분류표: 수집 목적과 보유기간

면접 설명 예시:

> 건강정보를 일반 콘텐츠와 같은 등급으로 보지 않고 D3로 분류했습니다. 기능을 추가할 때 수집 목적, 소유자 권한, 보유기간, 공개 집계의 재식별 가능성까지 먼저 검토하고, 권한 테스트·migration dry run·복원 훈련을 release gate로 두었습니다. 자동 테스트 통과와 운영 증거를 구분해 AWS 설정이나 백업 복원은 코드 구현만으로 완료 처리하지 않았습니다.

## 14. 최종 production 승인

다음 조건을 모두 만족해야 한다.

- [ ] 4절의 `BLOCK`이 0개다.
- [ ] 4절의 `DECISION`이 운영 책임자 승인으로 모두 확정됐다.
- [ ] `docs/go-live-checklist.md`가 완료됐다.
- [ ] `docs/templates/release-security-review.md`에 증거 링크가 있다.
- [ ] staging에 production과 같은 이미지 digest를 배포했다.
- [ ] D3 타인 접근, 공개 통계, 탈퇴·삭제, backup restore를 검증했다.
- [ ] 운영 책임자와 개발 책임자가 승인 시각을 남겼다.

새 기능, migration, 인증 방식, 인프라, 위탁사, 처리방침이 바뀌면 기존 승인은 만료된다.
