## 보안·운영 변경

- 관리자 MFA는 역할·사용자·로그인 토큰·credential version에 결합한 서버 검증이며 15분 만료다.
  TOTP 재사용/반복 실패/복구 코드 재사용을 차단한다. 최초 등록·분실 재등록에는 개별 승인 코드가 필요하다.
- 운영자가 일반 커뮤니티 API로 문의를 읽는 우회를 막기 위해 운영자 역할의 게시글·댓글·이미지 API에도
  MFA를 요구한다. 홈·커뮤니티·문의 화면은 인증 후 로드한다. 일반 회원에는 MFA를 요구하지 않는다.
- 감사 이력은 요청 본문·검색어·비밀값을 기록하지 않는다. 개발자 요청 진단은 최대 1시간/1000건이며
  회원 ID·IP·본문·쿼리 대신 요청 ID, 메서드, 경로 템플릿, 상태, 소요 시간만 제공한다.
- main의 V43을 보존하고 미적용 후보 마이그레이션을 V44(MFA), V45(감사 인덱스), V46(선택 서식)로 정리했다.
  실제 스테이징/운영 Flyway 이력 확인 전 적용하지 않는다.
- 6시간 백업·8/32/15일 보관과 일일 EBS 7개는 유지한다. 암호화 키를 단순 교체하지 않는다.
- 격리 복원은 중지된 스테이징과 새 암호화 임시 볼륨만 사용한다. 건강정보/MFA 복호화, 평문 잔존,
  마이그레이션, 합성 계정의 가입·로그인·글·댓글·일지 서비스를 확인하고 합성 데이터를 롤백한다.
  이는 실제 운영 브라우저 검증과 별개다. 복원 종료 시 원래 IAM profile 복구·임시 볼륨 정리·중지가 필요하다.
- Amplify 두 배포 경로의 동시 실행 그룹을 맞췄다. 동일 SHA 성공 빌드는 재사용하고 진행 중인 빌드는
  기다린다. 브랜치가 바뀌거나 커밋이 HEAD로만 확인되는 경우 완료로 인정하지 않는다.
- 스테이징 백엔드 검증은 current develop에서도 실행할 수 있다. production은 여전히 current main과
  정확히 일치하는 staging-passed 이미지 digest를 요구한다. 운영용 검증 조건을 완화하지 않는다.

## 운영 적용 중단점과 남은 조건

1. PR CI에서 실제 MySQL 마이그레이션·Linux 빌드/스크립트 검증을 통과시킨다.
2. AWS 로그인 후 서비스별 비용, 실행 이미지/DB migration, SSM, 보안그룹, 암호화, 백업 성공 마커,
   알림 구독과 기존 ECR 보호 이미지를 읽기 전용으로 확인한다.
3. 스테이징에서 후보 배포·실제 계정 권한/MFA·DB 저장·로그인/일지/댓글·격리 복원·정리/중지를 검증한다.
   운영 담당자를 확인해 최초 MFA 등록 승인을 준비한다. 모든 관리자에게 등록 승인을 열지 않는다.
4. 실제 iPhone Safari/Android 앱 WebView의 키보드·확대·safe area와 외부 메신저 공유를 확인한다.
5. 최종 커밋·PR·증적과 미통과 항목을 사용자에게 보여준 후 운영 적용 승인을 받는다.

승인 후에는 현재 운영 이미지 digest·migration을 재확인하고 배포 전 백업의 본체/체크섬/완료 마커와
복구 키 버전을 확보한다. 새 키·MFA 등록 절차·알람/복구 IAM 구성을 확인한 뒤 main 병합 및 배포한다.
배포 후 로그인·일지·게시글·댓글·관리 기능과 외부 HTTPS를 확인한다. 실패 시 기존 배포 스크립트의
previous-image로 롤백한다. 추가형 V44~V46은 되돌리는 SQL을 실행하지 않으며 기존 데이터/키를 유지한다.
롤백 버전의 MFA 지원 여부도 확인한다. MFA 도입 전 이미지로의 롤백은 동일한 관리자 보호를 보장하지 않으므로
기존 운영 버전의 보호 설정을 복원하고 관리자 경로를 다시 점검해야 한다.
