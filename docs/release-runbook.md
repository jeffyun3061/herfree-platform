# Herfree 배포/롤백 런북

## 브랜치와 커밋

- `main`: 운영 배포 기준
- `develop`: 사용자 운영 승인 전 후보 스테이징 검증 가능
- 작업 브랜치: 기능/보안 수정
- 운영 배포 전에는 백엔드 build와 프론트 lint/build가 모두 통과해야 한다.

## 배포 전 체크

```bash
cd backend
./gradlew build

cd ../frontend
npm run lint
npm run build
```

확인 항목:

- `.env.prod`가 git에 포함되지 않았는지
- `JWT_SECRET`, DB 비밀번호, SMTP 비밀번호, S3 키가 git에 없는지
- `APP_MAIL_MODE=smtp`
- `TRUSTED_PROXY_CIDRS`가 실제 프록시 CIDR만 가리키는지
- `CORS_ALLOWED_ORIGINS`가 실제 프론트 도메인인지
- 기존 Flyway 파일/체크섬이 일치하는지 (불일치 시 repair/덮어쓰기 금지)
- `ADMIN_MFA_REQUIRED=true`, 별도 MFA 암호화 키, 본인 확인된 관리자 최초 등록 승인 절차
- 배포 전 S3 백업 본체·체크섬·완료 마커·건강정보/MFA 복구 키 버전
- 운영 적용 전 사용자에게 최종 결과를 제시하고 승인받았는지

CI 통과 후 `develop` 후보를 staging에서 검증한다. 운영 승인 후 `main` SHA가 바뀌면 그 SHA도
staging에서 통과시킨다. production은 정확한 `staging-passed-<main SHA>`의 digest를 재사용한다.
명령·환경 준비는 [현재 AWS 배포 가이드](deployment-aws.md)와 [스테이징 실행서](staging-operations.md)를 따른다.

## 배포 후 smoke test

| 순서 | 테스트 | 기대 결과 |
|------|--------|-----------|
| 1 | 외부 `/api/health` | 200·환경 일치·request ID |
| 2 | 회원가입/로그인 | HttpOnly 세션·회원 화면 정상 |
| 3 | 비밀번호 재설정 | 실제 메일 수신 |
| 4 | 게시글 작성/수정/삭제 | 정상 처리 |
| 5 | 이미지 업로드/조회 | S3 저장 및 API 프록시 조회 |
| 6 | 문의/상담 게시판 | 본인 또는 운영자만 조회 |
| 7 | 관리자 MFA·신고 처리 | 미인증 차단·인증/만료·숨김/복구 정상 |
| 8 | 공개/회원 전용 공유 | 공개 제목/요약·비공개 공통 안내·로그인 후 원문 권한 재검사 |
| 9 | 익명 고민·댓글·신고 목록 | 닉네임·회원 ID 연결 비노출 |

## 롤백

1. 현재 장애 증상을 기록한다.
2. 직전 정상 배포 커밋을 확인한다.
3. 서버에서 직전 이미지/커밋으로 재배포한다.
4. DB migration이 포함된 배포라면 롤백 전 개발자가 migration 영향을 확인한다. 적용된 Flyway 파일을 바꾸거나 임의 역마이그레이션하지 않는다.
5. smoke test를 다시 수행한다.
6. MFA 도입 전 이미지로 복구했다면 MFA 보호가 동일하다고 간주하지 않는다. 관리자 경로의 기존 보호 설정을 복원하고 접근 차단을 확인한다.

## 장애 시 우선순위

1. 인증/로그인 장애
2. DB 연결 장애
3. 비밀번호 재설정 메일 장애
4. 이미지 업로드/조회 장애
5. 관리자 기능 장애

사용자 개인정보나 토큰이 로그에 노출된 정황이 있으면 즉시 배포를 중단하고 로그 접근 범위를 제한한다.
