# 배포 전 운영·퍼널·UX 점검 계획

이 문서는 첫 실서비스 배포 전에 개발자가 직접 결정해야 하는 항목과, 배포 후 유지보수하면서 볼 지표를 정리한다.
기본값은 `EC2 단독 배포`, `서버 이벤트 로그 기반 퍼널`, `핵심 플로우 집중 UX 검수`다.

## 1. 배포 전 직접 결정할 항목

| 항목 | 기본 결정 | 직접 확인할 것 |
| --- | --- | --- |
| 배포 구조 | EC2 단독 + Nginx + Docker Spring + MySQL | ALB 없이 시작할지, RDS를 첫 배포부터 쓸지 |
| 프록시 신뢰 | `TRUSTED_PROXY_CIDRS=127.0.0.1/32` | Nginx가 같은 EC2에서 Spring으로 프록시하는지 |
| DB migration | 앱 시작 시 Flyway 적용 | 배포 전 `mysqldump` 또는 RDS snapshot |
| rollback | 코드 rollback + DB 영향 확인 | 이미 적용된 migration을 되돌릴 수 있는지 |
| secret | `.env.prod` 또는 AWS 환경변수 | Git에 실제 secret이 없는지 |
| 메일 | `APP_MAIL_MODE=smtp` | 실제 비밀번호 재설정 메일 수신 |
| S3 | public access block + IAM role 우선 | 이미지 업로드/조회 smoke test |
| CORS | 실제 프론트 도메인만 허용 | preview 도메인을 허용할지 |

ALB로 전환하면 `TRUSTED_PROXY_CIDRS`는 ALB가 위치한 서브넷 CIDR만 허용한다.
`0.0.0.0/0`은 사용하지 않는다.

## 2. 배포 순서

1. `git status`로 의도하지 않은 변경 확인
2. 백엔드 `.\gradlew.bat test`, `.\gradlew.bat build`
3. 프론트 `npm run lint`, `npm run build`
4. 운영 secret과 `.env.prod` 확인
5. DB 백업 또는 snapshot 생성
6. 서버 배포와 Flyway migration 적용
7. health endpoint 확인
8. 핵심 smoke test 수행
9. 30분~1시간 로그 관찰

## 3. 서버 이벤트 로그 기반 퍼널

초기에는 GA4보다 서버 이벤트 로그를 우선한다.
개인정보 수집을 줄이고, 서비스 핵심 흐름만 확인하기 위해서다.

| 이벤트 | 의미 | 원문 저장 금지 |
| --- | --- | --- |
| `signup_started` | 회원가입 진입 또는 OAuth 가입 시작 | 이메일, OAuth code |
| `signup_completed` | 회원가입 성공 | 이메일, 약관 원문 |
| `login_succeeded` | 로그인 성공 | 비밀번호, token |
| `post_created` | 게시글 작성 성공 | 제목, 본문, 이미지 URL 원문 |
| `journal_created` | 새 일지 작성 성공 | 증상 메모, 상세 기록 |
| `password_reset_requested` | 활성 계정의 재설정 메일 요청 | reset URL, token, 이메일 원문 |
| `admin_action` | 관리자 조치 발생 | 사유 원문, 개인정보 |

운영 장애 추적 로그와 퍼널 이벤트는 목적을 분리한다.
장애 로그는 CloudWatch에서 원인 추적용으로 보고, 퍼널 이벤트는 `app_event_logs` 집계로 흐름만 본다.

## 4. 배포 후 주간 점검

| 주기 | 확인 항목 | 이상 신호 |
| --- | --- | --- |
| 매일 | 5xx, SMTP 실패, S3 실패 | 반복 실패, 특정 API 급증 |
| 매일 | 신고/문의 대기 | 장시간 미처리 |
| 매주 | 회원가입 시작 대비 완료 | 완료율 급락 |
| 매주 | 로그인 성공/실패 추세 | 비정상 실패 급증 |
| 매주 | 게시글/일지 작성 흐름 | 핵심 활동 급감 |
| 매주 | 관리자 조치 | 숨김/정지 급증 |

운영자가 처리해야 하는 문제와 개발자가 봐야 하는 문제를 분리한다.
예를 들어 신고 처리는 운영자 업무지만, SMTP/S3 반복 실패는 개발자가 봐야 한다.

## 5. 핵심 UX 검수

전체 화면을 한 번에 완벽히 보려고 하지 않는다.
첫 배포 전에는 처음 온 사용자가 막히지 않는지에 집중한다.

| 플로우 | 기대 결과 |
| --- | --- |
| 비회원 홈 -> 회원가입 | 서비스 목적, 가입 CTA, 약관 동의가 자연스럽게 이어짐 |
| 회원가입 -> 로그인 상태 | 가입 후 기본 진입 화면이 어색하지 않음 |
| 로그인 -> 글쓰기 | 인증이 필요한 이유가 명확하고 실패 메시지가 이해됨 |
| 커뮤니티 -> 게시글 상세 | 목록, 검색, 상세, 반응이 끊기지 않음 |
| 일지 작성 -> 대시보드 | 기록 완료 후 요약이 바로 반영됨 |
| 마이페이지 | 내 글, 계정, 로그아웃 위치를 쉽게 찾음 |
| 관리자 | 신고 처리, 숨김/복구, 회원 제한이 실수 없이 가능 |

검수 화면 크기:

- 모바일: 390px 너비
- 데스크톱: 1440px 너비

확인 기준:

- 텍스트가 잘리지 않는가
- 버튼이 너무 작거나 애매하지 않은가
- 로딩/빈 상태/오류 상태가 있는가
- 로그인 만료나 401 상황에서 사용자가 길을 잃지 않는가
- 비공개 데이터가 화면/API에서 노출되지 않는가

## 6. 배포 차단과 후속 개선 구분

### 배포 차단

- 운영 secret 누락
- DB 백업/복구 계획 없음
- SMTP 재설정 메일 미동작
- S3 이미지 업로드/조회 실패
- 회원가입/로그인 실패
- 비공개 게시판 타인 글 노출
- 관리자 API 일반 사용자 접근 가능
- 관리자 MFA 또는 VPN·Access Gateway·고정 IP 같은 대체 통제 없음
- 공개 건강 통계의 사용자 20명·항목 5명 기준 staging 검증 없음
- 탈퇴 후 동의·감사·게시물 보존기간과 재가입 정책 승인 없음
- RDS TLS·저장 암호화·복원 검증 없음

### 후속 개선

- GA4 또는 PostHog 고도화
- refresh token HttpOnly cookie와 회전
- 고급 감사 로그
- Playwright E2E 자동화
- ALB/RDS 분리 확장

## 7. 면접에서 설명할 포인트

> 첫 배포에서는 GA4 같은 외부 분석 도구보다 서버 이벤트 로그로 핵심 퍼널만 먼저 수집했습니다. 이메일, 토큰, 게시글 본문, 일지 메모 같은 민감 정보는 저장하지 않고, 회원가입·로그인·글쓰기·일지 작성·관리자 조치처럼 운영에 필요한 이벤트만 집계했습니다.

> 배포 전에는 Flyway migration, DB 백업, SMTP/S3 smoke test, 비공개 게시판 권한, 공개 건강 통계의 재식별 방지, 관리자 강한 인증 또는 대체 접근 통제를 배포 차단 항목으로 두었습니다. refresh token 회전은 현재 access token 만료와 sessionStorage 정책을 위험 수용 기록으로 남긴 뒤 기한을 정해 개선합니다.
